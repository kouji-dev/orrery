# Build-time changelog generation for the landing page

**Date:** 2026-06-13
**Status:** Approved (design)
**Author:** brainstormed with Claude

## Problem

The Orrery landing page (`landing/`) is already a hand-rolled, zero-dependency
static site deployed to Render. It ships frozen HTML with **no runtime GitHub
calls** — the changelog data is already baked in.

The one part that is **not** automated is the baking. `landing/changelog.html`
carries a hardcoded `const RELEASES = [...]` array (changelog.html:151-176) that
a human transcribes from `git log` at release time. This is tedious and
error-prone.

## Goal

Automate baking real commit data into the static changelog **when a release is
published**, while:

- Keeping the hand-rolled, zero-dependency site exactly as-is (no framework).
- Keeping the shipped page free of any runtime GitHub call (data stays baked).
- Letting a human supply the one editorial field that the API can't: a
  marketing `summary` line per release.

This is **static generation (SSG)** of the changelog data — fetch once in CI,
ship frozen HTML — not server-side rendering.

## Non-goals (YAGNI)

- No SSG framework (Astro/Eleventy). The hand-rolled site stays.
- No runtime fetch of any kind (not even same-origin JSON). Data is baked into HTML.
- No reading from the `kouji-dev/orrery-releases` distribution repo. Commits come
  from the main repo `kouji-dev/orrery`.
- No `channel` derivation — `dev` only for now (a workflow input, default `dev`).
- No auto-generated summaries — the human types them.
- Only `changelog.html` is generated. `index.html`, `home.js`, `console-mock.js`
  are untouched.
- Pagination is a **client-side reveal** of already-baked data — a "fake load
  more" — not a paged server fetch. No network of any kind.

## Key facts about the current setup

- `landing/` is served by Render as a pure static site from git `main`'s
  `./landing` folder (see `render.yaml`). Render deploys from **git**, not from a
  CI artifact — so generated content must land on `main` to ship.
- Git **tags + commits** (conventional-commit messages: `feat`/`fix`/`perf`/`ci`,
  scope, hash) live on `kouji-dev/orrery`. These map cleanly to the GitHub API.
- GitHub **Releases** (with notes + `prerelease` flag) are cut in a *separate*
  repo `kouji-dev/orrery-releases`. We deliberately do **not** depend on it.
- Tag = version: the git tag `vX.Y.Z` matches `package.json` version.

## Design

### 1. Marker region in `changelog.html`

Replace the hardcoded array (changelog.html:151-176) with a delimited region the
generator can rewrite. The existing entries become the seed history:

```js
/* RELEASES:START — generated by tools/landing/gen-changelog.mjs; do not hand-edit */
const RELEASES = [ /* existing 5 entries kept as seed */ ];
/* RELEASES:END */
```

Everything else in the file — the render loop (changelog.html:181), the styles,
the epicycle logo — is untouched.

### 2. Generator: `tools/landing/gen-changelog.mjs`

Node script, zero dependencies (uses global `fetch`).

**Inputs (CLI flags / env):**

| Flag | Required | Default | Meaning |
|---|---|---|---|
| `--summary` | yes | — | Marketing one-liner for the release being published |
| `--tag` | no | latest `v*` tag | Which release to add (`vX.Y.Z`) |
| `--channel` | no | `dev` | Release channel badge |
| `--dry-run` | no | off | Print the resulting `RELEASES` block, write nothing |

**Behavior:**

1. Resolve `--tag` (default: newest `v*` tag) and the **previous** `v*` tag to
   scope the commit range.
2. Fetch commits in `prevTag..tag` from `kouji-dev/orrery` via the GitHub API,
   authenticated with `GITHUB_TOKEN`.
3. Parse each commit message as a conventional commit →
   `{ type, scope, hash (short), msg }`. Messages that don't conform fall back to
   a `chore` bucket — the script never crashes on a malformed message.
4. Build **one** release entry:
   `{ tag, channel, date ("Month D, YYYY"), ref (short SHA of tag commit), summary, commits:[…] }`.
5. Read `changelog.html`, parse the existing `RELEASES` array from between the
   markers, **prepend** the new entry (or **replace** the entry if `tag` already
   exists — idempotent), re-serialize the array literal, write it back between
   the markers.

The script touches **only** the marker region; it does not reformat the rest of
the file.

### 3. Workflow: `.github/workflows/publish-changelog.yml` (new)

Trigger: `workflow_dispatch` only (manual — the only way to collect a typed
`summary`).

**Inputs:** `summary` (required), `tag` (optional, default latest),
`channel` (default `dev`).

**Permissions:** `contents: write`.

**Steps:**

1. Checkout `main` with full history + tags.
2. Run `node tools/landing/gen-changelog.mjs --summary "<input>" [--tag <input>] --channel <input>`
   with `GITHUB_TOKEN` in env.
3. If `landing/changelog.html` changed, commit it back to `main` with a
   `chore(landing): sync changelog [skip ci]` message and push, using the
   default `GITHUB_TOKEN`.
4. Fire the Render deploy API (same logic as `deploy-landing.yml`).

**Why no deploy loop:** pushes made with the default `GITHUB_TOKEN` do **not**
trigger new workflow runs, so committing `changelog.html` back to `main` won't
retrigger `deploy-landing.yml`. Because of that same rule, this workflow triggers
the Render deploy explicitly rather than relying on the push.

### 4. Client-side pagination ("fake load more")

All releases are baked into the `RELEASES` array, so pagination is purely a
display concern in `changelog.html`'s render code — no network, hence "fake."

- A `PAGE_SIZE` constant (default **5** releases per page).
- Initial render shows the first `PAGE_SIZE` entries only.
- A **"Load more"** button below the list reveals the next slice on click,
  appending to what's already shown.
- The button hides once every entry is visible.
- The total count (`relCount`, changelog.html:180) keeps showing the full number,
  so "Showing 5 of 12" style context is honest.

This lives entirely in the render block (changelog.html:181-200) and is
**independent of the generator** — the generator only rewrites the marker-delimited
data region, never the render loop. The two changes don't touch each other.

Note (future, not now): incremental prepend grows `RELEASES` unbounded over time,
so the baked HTML slowly grows. Acceptable for the foreseeable future; if it ever
matters, the generator can cap retained entries. Out of scope here.

## Data flow

```
human runs publish-changelog (types summary, picks/defaults the tag)
  → script fetches commits for prevTag..tag (GITHUB_TOKEN)
  → parses conventional commits
  → builds 1 release entry, prepends into changelog.html RELEASES (between markers)
  → commit back to main: "chore(landing): sync changelog [skip ci]" (GITHUB_TOKEN, no loop)
  → trigger Render deploy
  → Render serves ./landing — frozen HTML, zero runtime GitHub calls
```

## Error handling

- **Missing summary** → workflow input is `required: true`; GitHub blocks the run.
- **Tag not found / empty commit range** → script exits non-zero with a clear
  message; workflow fails; nothing is committed.
- **GitHub API rate limit** → `GITHUB_TOKEN` gives 5000 req/hr; one run makes 1–2
  calls. Non-issue.
- **No diff** (re-run same tag, identical data) → skip the commit; optionally skip
  the Render deploy too.
- **Malformed (non-conventional) commit message** → bucketed as `chore`; never
  crashes.

## Testing

Per the project rule "E2E after every feature":

1. **Vitest unit test** on the pure parse + inject logic (Vitest is already a dev
   dependency): conventional-commit parsing, prepend ordering, replace-on-same-tag
   idempotency, malformed-message fallback. The generator's pure functions are
   exported for this.
2. **Local dry run**: `node tools/landing/gen-changelog.mjs --tag v0.2.5 --summary "test" --dry-run`
   against real history; eyeball the emitted `RELEASES` block.
3. **Render check**: open the regenerated `changelog.html` locally
   (`npx serve landing`) and confirm it renders, and that **"Load more" reveals
   the next page and hides once all entries are shown**.
4. **Workflow smoke**: one `workflow_dispatch` run on a real tag; confirm the
   commit lands and the Render deploy fires.
