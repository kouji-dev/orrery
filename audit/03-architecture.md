# 03 — Architecture and maintainability

Audit pass 3, at v0.22.2. Seven lenses examined structure rather than defects; a second reviewer re-derived every count and tried to refute every claim. What survives: **34 high, 59 medium, 42 low**, plus one claim refuted and four reclassified as documented trade-offs, all listed at the end.

The question this pass asks is not "is this code good" but "what makes it hard to change safely, and what would a maintainer be unable to trust". Counts are measured, not estimated, and the measurements are reproduced in each finding. Single authorship, private beta, Windows-first, hand-maintained wire types and signal stores are context, not smells; where a decision has written rationale that holds up, it is marked as a trade-off rather than a finding.

## The short version

**The data model contains fiction that the UI faithfully renders.** `AgentStatus` declares six values; production writes exactly two. The consequence is not cosmetic: three of the four Orchestrator stat blocks and three of the four Kanban columns are permanently zero, because they filter on statuses nothing ever sets. `Agent.pending` is never populated, yet four separate "does this agent need me?" predicates branch on it — the sidebar dot, the rail badge, and two more. `Agent.commits` is hard-coded to `0` by the backend, is printed at ten sites, and gates the Push and Merge buttons, so an agent that commits its own work has Push disabled. Roughly a quarter of what the Orchestrator displays cannot become true.

**The frontend-backend contract is stringly typed, uncodegenned, untested, and already broken in two places.** 100 commands and 27 event channels are matched by hand between `bridge.ts` and `lib.rs`. Two `Settings` fields are silently discarded on every write: the frontend sends `toolPath` and `keymapTerminal`, the Rust struct has `toolPaths` and no terminal keymap at all. Because `settings_set` deserializes into the typed struct and re-serializes it, the keys vanish with no error, and both test suites stay green. That is the exact failure a contract test exists to catch, and there is none.

**Nothing verifies the backend.** CI runs `vitest` and nothing else — no `cargo test`, no clippy, no type-check, no build, no e2e. All 100 Tauri commands have zero test coverage, and the harness cannot host such a test today. 26 Rust tests are `#[cfg(windows)]`-gated while CI has no Windows runner, so the most Windows-specific logic in a Windows-first product can never run in CI even after you add `cargo test`. `clippy.toml` bans three APIs repo-wide and no workflow runs clippy; the repo's own integration test violates the ban. No tsconfig covers spec or e2e files, so 13,181 lines of test code are never type-checked, and nothing type-checks the app at all until a release tag has already been pushed. The single end-to-end hook test asserts a protocol the real bridge no longer speaks.

**The layering rule the project wrote for itself is broken.** The backend design spec states modules call down, never in cycles. Measured: 21 modules, 67 inter-module edges, and one strongly-connected component of nine — agents, fs, git, history, hooks, projects, runtime, search, watch — holding 22 of those edges. Only `core` and `perf` are true leaves. The git module imports agents and projects to resolve ids; the PTY runtime reaches into tickets and the entity-event layer from its wait thread.

**`project_remove` is a second, weaker copy of agent teardown — and it is the stated integrity mechanism.** A comment in the agents service records that there is deliberately no foreign key because "cascade-on-project-delete handled by remove_for_project". That function skips the disposal opt-in, the trash rename, the git deregistration, the process stop, the watcher unregister and the history purge that `agent_remove` performs, and deletes every worktree outright.

**Failures are invisible.** 47 log statements across 26,847 lines of Rust, one per 571 lines, three of them at error level; the git module has one log call in 4,816 lines. Against that: 116 `let _ =` discards, 52 `unwrap_or_default()`, and no panic hook anywhere, so a startup panic kills the app with no window and no log entry. Every entity CRUD event is emitted with `let _ =` and the stores never reconcile, so a single dropped emit desynchronises the UI permanently and silently. Agent exit status is discarded entirely. On the frontend, every IPC failure passes through one chokepoint that reduces it to a boolean and throws the message away. A user reporting "it stopped working" cannot be helped from what this app records.

**Documentation actively misleads.** 271 comments across 92 files defer their rationale to a roadmap whose stack section is wrong on all three technologies it names. `docs/` describes a mock-data prototype called ORCHESTRA under a directory that does not exist, and eleven files cite `orchestra.store.ts` as the source of truth. The README is the unedited Tauri template, and the mandatory pre-build step is documented nowhere. 101 MB of committed Windows build output sits in `src-tauri/target-test`, ignored by nothing.

**Duplication is concentrated in the places that drift.** Seven relative-time formatters across two epoch units and four bucket vocabularies, one of them tested. Three worktree-slug implementations with two separators and three length caps, none tested. Two Windows launch wrappers, only one of which applies the newline fix. Four identity-colour functions.


## High (34)

### 1. `agent_start` requires HookBridge state that setup only conditionally manages — the app's primary action can be dead with only a log line

`src-tauri/src/agents/commands.rs:313` — observability

**Why it matters.** lib.rs:159-164 manages `HookBridge` only inside the `Ok` arm; a bind failure just does `log::error!("hook bridge failed to start: {e}")` and setup continues. `agent_start` — the one command that launches an agent, the product's core action — declares `bridge: State<'_, HookBridge>`, so with the bridge unmanaged Tauri's argument extraction rejects every invoke of it before the body runs. The user sees the Start button do nothing, with an error the frontend has no case for and no code path anywhere that degrades to a hook-less launch. The author already knows this hazard: lib.rs:235-239 keeps `CostCache` managed even when the cost feature is compiled off precisely because "the registered `system_cost` command takes State<CostCache> and an unmanaged state would panic the invoke". The same reasoning was not applied one screen earlier to the far more important service.

  ```
  lib.rs:159-164 `match hooks::HookBridge::start(...) { Ok(bridge) => { app.manage(bridge); } Err(e) => log::error!(...) }`. agents/commands.rs:308-318 `pub fn agent_start<R: Runtime>(app, rt: State<RuntimeService>, svc: State<AgentService>, settings: State<SettingsService>, bridge: State<'_, HookBridge>, id, rows, cols, resume)`. `grep -rn "HookBridge>"` returns exactly one consumer. lib.rs:235-239 carries the contrary reasoning for CostCache. hooks/mod.rs:67 `TcpListener::bind("127.0.0.1:0")?` is the failure source.
  ```

**Also at.** `src-tauri/src/lib.rs:159`, `src-tauri/src/lib.rs:235`, `src-tauri/src/hooks/mod.rs:67`

**Direction.** Manage an `Option`-shaped or always-present HookBridge (a disabled instance when bind fails) as was done for CostCache, and have `agent_start` launch without hooks plus a user-visible notice rather than failing argument extraction.

<sub>Verifier: Verified line by line and nothing softens it. lib.rs:159-164 manages HookBridge only in the Ok arm and logs on Err. agents/commands.rs:308-318 declares `bridge: State<'_, HookBridge>` — Tauri resolves State during argument extraction, so an unmanaged HookBridge fails every agent_start invoke before the body runs. `grep -rn HookBridge src-tauri/src` shows agents/commands.rs:313 is the only non-test consumer of that state (the other 25 hits are hooks/mod.rs tests constructing bridges directly). ### 2. The stated "modules call down, never in cycles" rule is violated by a 9-module strongly-connected component

`src-tauri/src/git/branches.rs:15` — coupling

**Why it matters.** docs/superpowers/specs/2026-06-05-backend-foundation-and-projects-design.md:49 states the rule: "modules call *down* into others (e.g. `projects` uses `git`), never in cycles. Each module owns a service (managed state) + its commands." The actual graph, derived from every `crate::<module>` reference outside tests, has 21 top-level modules, 67 inter-module edges, and one SCC of 9 modules — agents, fs, git, history, hooks, projects, runtime, search, watch — holding 22 of those edges. Only `core` and `perf` are true leaves. The practical cost: there is no module you can read, change, or replace in isolation. Touching `git`'s types forces you through `agents`, `projects`, `watch`, `history` and `search`; touching `agents` reaches back into all of them. No later doc revises the rule, so this is drift, not a recorded trade-off.

### 4. `project_remove` is a divergent, incomplete second implementation of agent teardown

`src-tauri/src/projects/commands.rs:76` — duplication

**Why it matters.** Agent teardown exists twice with different behaviour, and the difference is invisible until a user deletes a project that has agents. `agent_remove` (agents/commands.rs:96-105) stops the PTY, drops the scrollback ring, unwatches the worktree, purges local history, then deregisters the git worktree and renames the folder aside with the Windows retry loop, honouring the KeepFolder default that types.rs:11-14 says exists "so a delete can never cost someone work they had not committed". `project_remove` does none of that: it deletes the agent rows and blows the directories away with a bare `std::fs::remove_dir_all`. Result of deleting a project with running agents: the PTY processes keep running with no owner row, the notify watchers keep firing `agent://changed` for ids the UI no longer knows, the history dirs leak, the main repo keeps stale `.git/worktrees` registrations, and uncommitted work in every worktree is destroyed with no confirm — the exact outcome the per-agent path is designed to prevent. On Windows the naive delete is also the one the codebase's own comment (git/service.rs:20-25) says routinely fails on the first attempt.

  ```
  projects/commands.rs:74-92: `svc.remove(id)?; if let Ok(removed) = agents.remove_for_project(id) { for aid in removed { emit_entity(... Change::Deleted ...) } }` — no RuntimeService, WatchService or HistoryService is even injected (the fn signature at :68-72 takes only AppHandle, ProjectService, AgentService). agents/service.rs:499-518 `remove_for_project`: `DELETE FROM agents WHERE project_id = ?1` then `for r in &recs { let _ = std::fs::remove_dir_all(&r.worktree); }` — no `WorktreeDisposal`, no `trash_path`/`rename_retry`, no `remove_dir_all_retry`, no `git.remove_worktree`. Contrast agents/service.rs:400-446 (`remove`) which does all five.
  ```

**Also at.** `src-tauri/src/agents/service.rs:499`, `src-tauri/src/agents/commands.rs:96`, `src-tauri/src/git/service.rs:20`, `src-tauri/src/git/types.rs:11`

**Direction.** Make `project_remove` loop over `agents.ids_for_project(id)` and call the same teardown path `agent_remove` uses (or move that teardown into a single service-level `AgentService::teardown(id, ...)` both commands call), so there is one implementation of "an agent goes away".

<sub>Verifier: Every element checked and true. projects/commands.rs:67-72 takes only AppHandle, ProjectService and AgentService — no RuntimeService, WatchService or HistoryService is in scope, so rt.stop/rt.drop_scrollback/watch.unwatch/history.purge (all four present in agents/commands.rs:96-105) cannot happen. agents/service.rs:499-518 remove_for_project does `DELETE FROM agents WHERE project_id = ?1` then `let _ = std::fs::remove_dir_all(&r.worktree)` with no WorktreeDisposal, no trash_path/rename_retry, no git.remove_worktree — contrast agents/service.rs:406-441 which does all of it. ### 5. No test runs anywhere on the release path, and on the manual-dispatch path the published commit is tested by nothing at all

`.github/workflows/release.yml:82` — ci-release-gating _(added by verifier)_

**Why it matters.** Orrery ships an auto-updater (tauri.conf.json:46-51 points at a public latest.json endpoint), so whatever a tag builds installs itself on users' machines. Nothing gates that. release.yml has four jobs — prepare (:38), build (:82), publish (:140), changelog (:187) — and none of them runs vitest, playwright, cargo test or a typecheck; build goes straight from `pnpm install` to `pnpm tauri build` (:110-115). The local entry point is no better: bump.mjs's only precondition is a clean working tree (:32-35), after which it stamps, commits, tags and pushes (:38-55). On the tag-push path test.yml happens to fire in parallel because the bump commit also lands on main, but it is a race, not a gate — release.yml never waits on it. On the manual-dispatch path it does not fire at all: release.yml:53-58 runs bump.mjs inside CI and pushes the commit with GITHUB_TOKEN, and the workflow's own header at :8-9 states that 'the GITHUB_TOKEN tag push does not re-trigger this workflow' — the same suppression applies to test.yml, whose triggers are only `push: {branches: [main]}` and `pull_request` (test.yml:2-4). So a dispatch release builds, signs, publishes and auto-updates a SHA that no workflow has ever tested. Combined with findings 02 and 03 (no typecheck, no cargo anywhere), the strongest statement that can be made about a shipped Orrery build is that its 61 vitest specs may have passed on some earlier commit.

  ```
  .github/workflows/release.yml:34-38 'jobs:' / 'prepare:'; :82 'build:'; :110-115 '- run: pnpm install --frozen-lockfile' then 'run: pnpm tauri build' — `grep -n '^  [a-z-]*:' .github/workflows/release.yml` -> prepare:38, build:82, publish:140, changelog:187, no test job
  .github/workflows/release.yml:8-9 '(The GITHUB_TOKEN tag push does not re-trigger this workflow, so there is no double run.)'
  .github/workflows/release.yml:53-58 'Bump version (dispatch only …) run: node scripts/release/bump.mjs ${{ inputs.bump }}'
  .github/workflows/test.yml:2-4 'on: / push: { branches: [main] } / pull_request:' (no `tags:` trigger)
  scripts/release/bump.mjs:32-35 only checks `git status --porcelain`; :38-44 stamp, commit, tag; :55 push branch + tag
  src-tauri/tauri.conf.json:29 'createUpdaterArtifacts': true; :46-51 updater endpoint + pubkey
  ```

**Direction.** Make `build` depend on a job that runs `pnpm test` (and, once findings 02/03 are addressed, typecheck + cargo test) on `needs.prepare.outputs.sha`, so the SHA that gets signed and published is the SHA that passed. Add the same check to bump.mjs before it tags, so a local `pnpm release` cannot push a red tree.
