# 04 — UX and product experience

Audit pass 4, at v0.22.2. Eight lenses read the frontend as a product rather than as code; a second reviewer then re-opened every cited template and refuted what the code did not actually do. What survives: **71 high, 115 medium, 38 low**, and one item reclassified as a defensible trade-off.

You asked for the critique a skeptical designer would give rather than reassurance, so that is what this is. Nothing here was observed in a running app — the app cannot be launched in this container — so every claim is derived from the template and the logic that produces the screen, with `path:line`. Full detail is given for the high findings; medium and low are one line each, with everything in `.audit-work/pass4-merged.json`.

## The short version

**The supervision loop — the entire reason this product exists — does not reliably tell you when an agent needs you.** This is not a polish problem, it is the product's core claim, and five independent defects undermine it. A Cursor agent waiting for approval is invisible by construction, because Cursor emits no permission hook and the PTY-heuristics fallback is not enabled for it. An agent that *finishes* raises nothing, because "finished" is wired to process exit and these CLIs do not exit. A crashed agent produces the same green "finished — review or merge its work" card as a successful one, with Push one click away. If a second permission request arrives while the first is unanswered it is silently dropped, so the Accept button approves a command the user never saw. And every dedicated "an agent needs you" indicator in the status bar filters on a status string the backend never writes. The one thing a user buys this app to do is the thing it is least able to guarantee.

**A new user's first click is a dead button.** With zero projects, the primary control — "Agent" in the sidebar, "Spawn" in the Orchestrator, the command palette entry, all five entry points — dereferences `projects.all()[0].id` and throws inside an effect, so nothing happens and nothing is shown. Clicking again throws again. There is no empty state anywhere in the app: the landing tab is four zeros above a blank grid. Three seconds after first launch a UAC dialog appears naming "Windows PowerShell", never Orrery, with no explanation before, during or after. First launch also rewrites four config files in the user's home directory without telling them, and replaces one entirely if it fails to parse.

**Failed actions routinely look like successes.** A spawn whose worktree could not be created still reports "spawned" and produces a normal-looking agent row. A failed git scan renders as "no changes", so a broken repo is indistinguishable from an idle agent. If the project or agent list fails to load at boot, the app renders as a pristine fresh install with no error at all. "Pull latest" flashes "pulled <project>" and never calls the pull command that exists two files away. The executable-path override in Settings verifies, turns green, and is then silently discarded by the backend. When a real error does surface, it is a 2.6-second line in the footer.

**Forms lose typed work.** The spawn modal closes before the await, so a failed spawn destroys the prompt the user just wrote. Any ticket change anywhere silently reverts the ticket you are editing, mid-sentence. A failed ticket save discards what you typed. Send review deletes the comments *before* delivery, and delivery is a blind paste that can fail silently.

**The app is not keyboard operable.** The sidebar — the primary navigation — cannot be reached or operated by keyboard at all. Neither can workspace tabs, the file tree, or the Orchestrator in any of its three views. There is no live region anywhere, so every toast, error and agent state change is silent to a screen reader. Agent status is conveyed by hue and blink rate alone, with blocked and done as red and green. The two overlays that exist to unblock an agent — the peek queue and the question stepper — have a dialog role that never takes focus and radios whose keyboard selection is thrown away.

**The landing page sells things the product does not do.** The console mock invents a CI integration and the feature list promises "merge only what passes", which no code implements. A Mac visitor's primary action downloads a Windows `.exe`. Nothing warns that the installer is unsigned, so the screen after Download is "Windows protected your PC". The second-most-prominent hero CTA points at a private repo and 404s for everyone. The prerequisites — you must already have the agent CLIs installed — are spelled out for AI crawlers in `llms.txt` and hidden from humans.

**The conflict resolver dead-ends.** Restart mid-merge and it calls the other branch "incoming", calls a rebase a merge, and calls a failed read "no merge in progress". A conflict without diff3 markers can never be staged. Resolve the last conflict, restart, and the merge can never be committed: the resolver reports no conflicted files and Commit stays dead.

## What I am not counting against you

Documented decisions with rationale that hold up: hooks are fire-and-forget so allow/deny are best-effort keystrokes; Windows-first; no fan-out, mobile, remote or embedded browser; decorator inputs where the test runner forces them. The Defender exclusion itself is well argued in its module header — what is missing is telling the user it is happening, not the decision to do it.

### 10. An agent finishing its work raises nothing — "finished" is wired to process death, and these CLIs never exit

`src/app/agents/agent-runtime.service.ts:193` — notification _(added by verifier)_

**When it bites.** The user gives five agents a task each and goes to lunch. Four of them finish. Nothing happens: no toast, no sound, no bell badge, no queue entry. Their cards say "running" in the pill with "idle" inside the ring, exactly like the fifth agent that is still thinking between tool calls. **What the code does.**

**A good version.** TurnEnd is the completion signal for a REPL agent: raise a `done` notification on the idle ping (deduped against the previous turn), so the toast, the cue, the bell and the queue all fire when the work is actually done.
